## 1. Требования

1. **Два полноценных приложения**: ПК (установщик с выбором пути, ярлык, автозапуск) и Android (APK).
2. **Синхронизация через свой GitHub-репозиторий**: карточки, картинки, прогресс, настройки.
3. **Иерархия групп любой глубины**: группа → подгруппа → подгруппа → … Карточки могут лежать
   на любом уровне. Пример: `Здоровье` → `Биомеханика` / `Анатомия` / `Физиология` → карточки.
   Пустая группа без карточек — допустима.
4. **Группа**: название + картинка-обложка.
5. **Карточка**: лицевая и обратная сторона, на каждой — текст и картинка.
6. **Самопроверка**: по всем группам сразу, по выбранным группам, по части группы.
7. **Три варианта ответа**: «вообще не помню» / «что-то помню» / «хорошо».
8. **Еженедельный отчёт**: сколько дней подряд заходил, сколько карточек по дням.
9. **Локальные уведомления** по расписанию пользователя (день недели + время), на ПК и Android.
10. **Голос убрать полностью** (озвучка, запись голоса, распознавание речи).
11. **Камера на телефоне**: и сфотографировать, и выбрать из галереи.
12. **Настройки синхронизируются** через репозиторий (исключения — §5.5).
13. **Коммит на каждое изменение**: создал карточку/группу — сразу коммит; изменил — коммит.
14. **Настраиваемая политика синхронизации**: при запуске приложения / по расписанию
    (день + время, например 03:00) / по кнопке. Варианты комбинируются.
15. **Миграция данных с любой старой версии на любую новую** — обязательна и не должна терять данные.
    Обратная совместимость (новый формат → старое приложение) не требуется, но старое приложение
    **не имеет права испортить** новые данные.
16. **Автообновление приложений** из GitHub-релизов с плашкой внутри приложения — ПК и Android.
17. **Инструкция пользователю** по созданию репозитория и подключению обоих приложений.

### 1.1. Два репозитория (решено)

| Репозиторий | Что внутри | Доступ |
|---|---|---|
| `Bablakov/flashcards` | исходный код + релизы (`.exe`, `.apk`) | **публичный** (решение пользователя 18.08) |
| `Bablakov/flashcards-data` | личные карточки, картинки, прогресс, настройки | **приватный**, создаётся отдельно |

Публичный репозиторий кода означает: автообновление скачивает релизы без токена,
на Android не нужен обходной путь с авторизованной загрузкой APK.

## 3. Исследование: как устроено запоминание в приложениях

### 3.1. Общие принципы

- **Active recall** — сначала вспомнить, потом увидеть ответ.
- **Spacing** — показывать карточку в момент, когда она вот-вот забудется.
- **Desirable difficulty** — повтор должен даваться с усилием.
- **Interleaving** — перемешивать темы в одной сессии.
- **Daily limits** — иначе после перерыва вываливается 300 карточек и пользователь бросает.
- **Retention target** — обычно 0.9: повтор планируется на момент, когда вероятность вспомнить падает до 90%.

### 3.2. Алгоритмы

| Алгоритм | Год | Как работает | Где | Минусы |
|---|---|---|---|---|
| **Leitner** | 1972 | 5 коробок, фиксированные интервалы 1/2/4/7/14 дней | физические карточки | все карточки в коробке равны, интервалы не адаптируются |
| **SM-2** | 1987 | у карточки свой ease factor, интервал = предыдущий × ease | Anki (классика), Mnemosyne | «ease hell»: после серии ошибок ease падает навсегда |
| **FSRS** | 2023+ | модель памяти DSR: Difficulty, Stability (сколько дней держится), Retrievability. Обучена на 700+ млн повторов | Anki (встроен, рекомендуемый), RemNote | сложнее; персонализация параметров — после ~1000 повторов |
| **HLR** | 2016 | «период полураспада» слова в памяти | Duolingo | заточен под язык и большой поток данных |

FSRS даёт ту же удерживаемость, что SM-2, за **20–30% меньше повторов**; сложность карточки
возвращается к норме после серии успехов, поэтому «ease hell» отсутствует.

**Берём FSRS** через `ts-fsrs` (TypeScript, MIT, чистая функция без сети — идеально для offline и JSON в git).

## 4. Наш алгоритм

### 4.1. Три кнопки

| Кнопка | FSRS | Что происходит |
|---|---|---|
| **Вообще не помню** | `Again` | stability обрушивается, карточка всплывает в этой же сессии и завтра, уровень падает |
| **Что-то помню** | `Hard` | интервал растёт минимально — карточка остаётся на своём уровне |
| **Хорошо** | `Good` | stability растёт, следующая встреча заметно позже, уровень выше |

Четвёртая оценка FSRS (`Easy`) не используется.

### 4.2. Уровни 1–5 — только для отображения

Вычисляются из `stability`, руками не меняются:

| Уровень | Stability | Подпись | Цвет (`BOX_COLORS` уже есть) |
|---|---|---|---|
| 1 | < 1 дня | Новая | красный |
| 2 | 1–3 дня | Учу | оранжевый |
| 3 | 3–7 дней | Закрепляю | жёлтый |
| 4 | 7–21 день | Знаю | зелёный |
| 5 | ≥ 21 дня | Выучено | циан |

Готовность группы = доля карточек уровня 4–5, **с учётом всех вложенных подгрупп**.

### 4.3. Новые карточки и лимиты

Шаги обучения: показ → +10 минут в той же сессии → +1 день → обычное расписание FSRS.
Лимиты по умолчанию: 20 новых и 100 повторов в день (настраиваются, синхронизируются).

### 4.4. Режимы самопроверки

| Режим | Что берёт | Влияет на прогресс |
|---|---|---|
| **Повторение** | созревшие на сегодня | да |
| **Новые** | ни разу не показанные | да |
| **Тренировка** | любой набор по фильтрам | нет |
| **Экзамен** | весь набор подряд, в конце отчёт | опционально |

**Область**: все группы / отмеченные группы / одна группа. Выбор группы по умолчанию
**включает все её подгруппы** (галочка «только эта группа, без вложенных» — рядом).
**Часть группы** — фильтры: уровни 1–5, только новые, только с ошибками, теги,
диапазон, случайные N.
**Направление**: лицевая→обратная / обратная→лицевая / вперемешку.

## 5. Структура данных

### 5.1. Иерархия групп

Хранение **плоское**, иерархия — логическая, через ссылку на родителя:

```
meta.json                              # версия формата данных
settings.json                          # синхронизируемые настройки
groups/<groupId>.json                  # { id, name, parentId, cover, order, color, deleted }
cards/<cardId>.json                    # { id, groupId, front, back, tags, deleted, createdAt, updatedAt }
media/<sha256>.webp                    # общий пул: имя файла = хеш содержимого
journal/<deviceId>/2026-08.jsonl       # ответы, только дописывание
```

Почему не вложенные папки в репозитории: перемещение группы означало бы массовое
переименование файлов на диске — это гарантированные конфликты при работе с двух устройств.
С `parentId` перенос ветки = правка **одного маленького файла**.

- Глубина не ограничена (в интерфейсе предупреждаем начиная с 5 уровней).
- Карточка может лежать в группе любого уровня; группа без карточек допустима.
- При загрузке проверяется отсутствие циклов (A → B → A) и «сирот» (`parentId` не существует →
  группа поднимается в корень, а не пропадает).
- Обложка и цвет есть у группы любого уровня.
- Статистика агрегируется вверх по дереву.

### 5.2. Почему один файл на объект

Добавление карточек на ПК и на телефоне без синхронизации создаёт **разные файлы** →
git сливает их без конфликта. Это прямой ответ на требование §1.13 и на опасение
«параллельное добавление сломает коммиты».

- **Удаление — мягкое** (`deleted: true` внутри файла). Иначе возникает конфликт
  «удалено там / изменено тут» — единственный, который git не решает сам.
  Физическая чистка — отдельной командой раз в несколько месяцев.
- **Медиа по хешу содержимого**: два устройства физически не могут создать разные файлы
  с одинаковым именем → бинарных конфликтов не существует. Пул общий, поэтому перенос
  карточки между группами не трогает картинки. Раз в N запусков — сборка мусора:
  удаление медиа, на которые не ссылается ни одна живая карточка.
- Единственный оставшийся конфликт — правка **одной и той же** карточки на двух устройствах;
  решается правилом «побеждает свежий `updatedAt`» (`lib/merge.ts` уже это умеет).

### 5.3. Прогресс — журнал событий

Строка журнала: `{"t":"2026-08-18T09:12:03Z","card":"abc","rating":"good","elapsed":4200}`.

Каждое устройство пишет **только в свой файл** `journal/<deviceId>/<месяц>.jsonl` →
git-конфликт невозможен в принципе, даже если оба устройства неделю были офлайн.
Актуальное состояние карточки (stability, difficulty, due) **вычисляется** проигрыванием
журнала и кэшируется локально в IndexedDB; кэш в git не коммитится.

Побочная выгода: из журнала бесплатно получаются отчёт (§8) и — в будущем — переобучение
параметров FSRS под себя.

### 5.4. Оффлайн

При такой схеме прохождение офлайн так же безопасно, как добавление карточек: ломать нечего.
Поэтому офлайн разрешено всё, а вместо запретов — индикатор «N несинхронизированных изменений».
Тумблер «строгий режим: не засчитывать прохождение без синхронизации» есть, но по умолчанию выключен.

### 5.5. Какие настройки синхронизируются

**В репозитории** (`settings.json`): расписание уведомлений, политика синхронизации (§7),
лимиты новых/повторов, целевая удерживаемость, режимы сессий по умолчанию, тема,
строгий офлайн-режим.

**Только на устройстве** (в git не попадает):
- **Personal Access Token** — секрет, в репозиторий не коммитится никогда;
- **адрес репозитория, ветка, имя и e-mail коммитера** — иначе «курица и яйцо»:
  чтобы прочитать настройки из репозитория, надо сначала знать, где он;
- **идентификатор устройства** (нужен для журнала);
- **тумблеры уровня ОС**: автозапуск, трей, разрешение на уведомления,
  «показывать уведомления на этом устройстве» (расписание общее, глушилка — локальная).

## 6. Совместимость версий и миграции

Требование §1.15: миграция с любой старой версии на любую новую, без потери данных.

### 6.1. Цепочка миграций

`meta.json` хранит `formatVersion` (целое число). В коде — список миграторов:

```
migrations = [ {from: 1, to: 2, up}, {from: 2, to: 3, up}, ... ]
```

Приложение при запуске применяет **все** миграторы по порядку от версии репозитория
до своей. То есть переход 1 → 5 = четыре последовательных шага, отдельный код «1→5»
писать не нужно, и любая старая версия данных доедет до текущей.

Правила для каждого миграгора:
- **идемпотентность** — повторный запуск ничего не ломает (важно, если синхронизация
  оборвалась посередине);
- **только добавление и преобразование**, никакого удаления полей «за ненадобностью»;
- перед миграцией — отдельный git-коммит `checkpoint before migration vN→vM`, чтобы откат
  был обычным `git revert`; плюс предложение выгрузить `.fcdeck`;
- после успеха — коммит `migrate data vN→vM` с новым `formatVersion`.

### 6.2. Старое приложение не должно портить новые данные

Две независимые защиты:

1. **Режим только чтения.** Если `formatVersion` в репозитории **выше** поддерживаемой,
   приложение показывает плашку «Данные созданы более новой версией — обновите приложение»
   и блокирует запись. Повторять карточки при этом можно, ответы копятся локально
   и отправятся после обновления.
2. **Сохранение незнакомых полей.** Схемы чтения не отбрасывают неизвестные ключи, а
   переносят их при записи обратно. Даже если защита №1 будет обойдена, старая версия
   не сотрёт поля, которых не понимает.

### 6.3. Миграция с текущего формата (0.1.0)

`cards.json` разбирается на файлы карточек; каждая колода становится группой верхнего уровня
(`parentId: null`); `box` и счётчики превращаются в стартовое FSRS-состояние по таблице §4.2;
медиа переименовывается в хеши; речевые настройки отбрасываются. Это миграция `1 → 2`.

## 7. Коммиты и синхронизация

### 7.1. Коммит на каждое изменение (требование §1.13)

| Событие | Когда коммит | Когда push |
|---|---|---|
| Создана/изменена/удалена карточка | **сразу** | через 3 секунды тишины (пачкой, если правок несколько подряд) |
| Создана/переименована/перемещена группа | **сразу** | там же |
| Изменены настройки | сразу | там же |
| Ответы в сессии | пачкой: каждые 30 секунд и в конце сессии | вместе с push |

Ответы копятся пачкой намеренно: коммит на каждую из сотни карточек в сессии превратил бы
историю в мусор, а конфликтов там нет по определению (§5.3), так что смысла в поштучных коммитах нет.
Всё остальное — поштучно, с человекочитаемым сообщением (`add card «Аорта» → Здоровье/Анатомия`).

Офлайн: коммиты делаются всегда, push просто откладывается до сети. Индикатор показывает,
сколько изменений ждёт отправки.

Про размер истории: тысячи мелких коммитов для git не проблема; клонирование новых устройств
идёт с `depth=1`. Если через годы история разрастётся — отдельная команда «сжать историю».

### 7.2. Когда синхронизироваться (требование §1.14)

Настройка комбинируемая, все варианты можно включить одновременно:

- ☑ **при запуске приложения**;
- ☑ **по расписанию** — таблица дней недели + время (например ежедневно 03:00,
  как у уведомлений; можно выбрать конкретные дни);
- ☑ **после изменений** — авто-push через 3 секунды тишины (п. 7.1);
- ☑ **при выходе / сворачивании**;
- **кнопка «Синхронизировать сейчас»** — всегда доступна.

Настройки синхронизации лежат в `settings.json` и переезжают на второе устройство.

## 8. Отчёт и уведомления

### 8.1. Экран «Отчёт»

Считается из журнала (§5.3), дополнительных данных хранить не нужно:

- **Серия** — сколько дней подряд были повторы, лучшая серия;
- **Неделя** — столбики по дням: карточек, минут, доля «хорошо»;
- **По группам** — уровни, % выученного, что созреет завтра и на неделе (с учётом подгрупп);
- **Прогноз нагрузки** на 7 дней вперёд.

### 8.2. Уведомления

Локальные, **без сервера и без FCM**: расписание живёт на устройстве и работает без интернета.
Настройка — таблица пн–вс: галочка + время у каждого дня.

| Платформа | Как | Ограничения |
|---|---|---|
| **Android** | `@capacitor/local-notifications`, повтор `on: {weekday, hour, minute}` | Android 13+ — разрешение `POST_NOTIFICATIONS`; Android 14 — точное время требует `USE_EXACT_ALARM`, пользователь может его отключить → проверять `checkExactNotificationSetting()` и деградировать до неточного времени |
| **ПК** | нативное уведомление Windows + свой планировщик | приходит, только если приложение запущено → автозапуск при входе в систему и сворачивание в трей вместо закрытия (оба с тумблерами) |

Текст осмысленный: «К повторению: 34 карточки (Здоровье/Анатомия — 20, История — 14)».

## 9. Автообновление приложений

Проверка раз в сутки и по кнопке: запрос к
`https://api.github.com/repos/Bablakov/flashcards/releases/latest`, сравнение с версией
приложения. Без интернета проверка молча пропускается.

- **ПК**: `electron-updater` + GitHub Releases. CI по тегу `v*` публикует установщик и `latest.yml`;
  приложение качает обновление в фоне и предлагает перезапуститься.
- **Android**: Play-Маркета нет. Плашка «Доступна версия 1.1» → скачивание APK из релиза →
  системный диалог установки поверх старой версии, данные сохраняются.

**Критично:** все APK подписываются **одним и тем же keystore**, иначе Android откажется
обновлять поверх и придётся удалять приложение вместе с локальными данными. Keystore
генерируется один раз, хранится в GitHub Secrets **и в личном бэкапе**. `versionCode`
увеличивается из номера сборки CI.

Связка с §6: приложение обновляется на одном устройстве раньше, чем на другом — это норма,
защиту даёт версия формата данных.

## 10. ПК-приложение

- **Electron + electron-builder**, установщик NSIS: `oneClick: false`,
  `allowToChangeInstallationDirectory: true` (выбор пути), ярлыки на рабочем столе и в «Пуск», деинсталлятор.
- **Git без CORS**: запросы `isomorphic-git` уходят по IPC в main-процесс и выполняются
  обычным Node-HTTP. Токен не покидает устройство, сторонний прокси не нужен.
- **Трей + автозапуск** — для уведомлений и фоновой синхронизации по расписанию.
- **Только один экземпляр приложения** (`app.requestSingleInstanceLock()`). Хранилище
  держит дерево файлов в памяти вкладки и сбрасывает его на диск с задержкой: два
  одновременно открытых окна на одних данных затирают правки друг друга. Проверено
  на практике 18.08 — карточка, созданная в одном окне, исчезла после записи из второго.
  То же ограничение действует для веб-версии: не открывать её в двух вкладках.
- Сборка в CI на `windows-latest`, артефакт `.exe`, при теге `v*` — GitHub Release.
- Хранилище — тот же IndexedDB-клон репозитория, что и на телефоне (одна кодовая база).

## 11. Android

- Плагины после чистки: `@capacitor/camera` (фото + галерея), `@capacitor/app` (кнопка «Назад»),
  `@capacitor/local-notifications`. TTS и диктофон удалены.
- Разрешения: `CAMERA`, `POST_NOTIFICATIONS`, при необходимости `USE_EXACT_ALARM`.
  `RECORD_AUDIO` больше не нужен.
- Git — через нативный HTTP мимо CORS; резерв — свой http-клиент для `isomorphic-git`.
  **Проверить в первую очередь** (бинарные тела запросов git-протокола).
- Подписанный `bundleRelease`: keystore → GitHub Secrets → signingConfig.

## 13. Инструкция пользователю (пишется в фазе 8)

Файл `SETUP-USER.md` + тот же текст внутри приложения на экране первого запуска:

1. Создать **приватный** репозиторий `flashcards-data`, пустой, без README.
2. Создать fine-grained токен: доступ только к этому репозиторию, права `Contents: Read and write`,
   максимальный срок жизни. Скопировать (показывается один раз).
3. **ПК**: скачать установщик из релизов → установить (путь выбирается) → Настройки → Git →
   адрес, ветка, имя, e-mail, токен → «Клонировать».
4. **Телефон**: скачать APK из релизов → разрешить установку → ввести **те же** данные → «Клонировать».
5. Настроить расписание уведомлений и политику синхронизации — они переедут на второе устройство сами.
6. Правила: синхронизация идёт сама; после долгого офлайна открыть приложение при сети и
   дождаться значка «синхронизировано»; независимый бэкап — экспорт `.fcdeck`.
7. Если что-то испорчено: удалить локальную копию → «Клонировать» заново; история версий —
   прямо на github.com.

## 14. Открытые вопросы

1. **Целевая удерживаемость FSRS** — по умолчанию 0.9, ползунок 0.85–0.95 в настройках.
2. **Переобучение параметров FSRS** под себя — журнал для этого есть, оптимизатор тяжёлый;
   не в 1.0, позже кнопкой «Пересчитать под себя».
3. **Двусторонний прогресс** (отдельные состояния для двух направлений) — не в 1.0.
4. **Размер репозитория от картинок** — на 1.0 приемлемо; дальше сжатие истории или git-lfs.
5. **Перенос карточек между группами массово** (мультивыбор) — желательно, но можно в 1.1.
